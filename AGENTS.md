# Repository Guidelines

## Project Structure & Module Organization
This Maven project keeps code under `src/main/kotlin/rayTraceTypescript`, split into domain-focused packages such as `materials`, `objects`, and `utils`. The entry point is `Main.kt`, which wires up the `Camera`, scene configuration, and invokes `render`, producing `image.ppm` in the repo root. Build artifacts land in `target/`, and `pom.xml` pins Kotlin 2.2.21 plus the Exec plugin that targets `rayTraceTypescript.MainKt`. Keep any future assets (sample renders, textures) in a dedicated top-level folder so they do not pollute `target/`.

## Rendering Backends
Ray tracing runs on an NVIDIA GPU through CUDA (LWJGL's `lwjgl-cuda`: the driver API from `nvcuda.dll`, which the driver installs, and NVRTC from `native/cuda/windows-x64`, see its README - no CUDA Toolkit needed). The kernel is CUDA C++ in `src/main/resources/kernels/raytracer.cu`, compiled at run time by `gpu/CudaContext` for the card found (sm_61 on a GTX 1070) with the scene's features switched in; `gpu/CudaSession` holds the scene in device memory behind the `gpu/GpuSession` interface. `Camera.initialize()` produces the shared `CameraSetup`, `gpu/SceneFlattener` lays the scene out as flat buffers, and the kernel does sampling, BVH traversal, materials and textures; the CPU only writes the PPM through `render/PpmWriter`. There is no other backend and no fallback: without a CUDA device a render fails with the reason. `RT_GPU_DEVICE=<substring>` picks a device by name (`RT_OPENCL_DEVICE` is still read); `-Drt.nvrtc=<dir>` / `NVRTC_DIR` point at another NVRTC 12.x (e.g. a toolkit's `bin`), `-Drt.cuda.options`, `-Drt.cuda.log`, `-Drt.cuda.dump=<file>` and `-Drt.cuda.ptx` are for compiler experiments. The kernel began as a port of the OpenCL kernel that preceded it (last in commit `1b65ee9`); on a GTX 1070 it traces about 15% slower than that one did (Yennefer at 256 spp: 11.7 s of GPU time vs 10.1 s) with near-identical machine code, and Nsight Compute does not support Pascal, so the cause is unknown. The CPU path tracer that preceded both is gone too; its renders of the comparison scenes are kept as test references (`src/test/resources/cpu-reference`, `reference-image*.ppm.gz`). The scene classes keep their CPU `hit` code, which the viewer's picking and placement use. Because the GPU draws its random numbers per pixel and sample, renders match those references in geometry, shading and brightness but carry a different noise pattern - compare images statistically (as `GpuCpuComparisonTest` does), never byte for byte. Instances: the CPU classes transform rays at traversal time, the flattener folds the same rigid transform into the primitives.

## Meshes and 3D File Formats
`objects/MeshLoader` reads a model file into a `Mesh` - a flat triangle soup - picking a parser in `objects/formats` by extension: STL (binary and ASCII, told apart by file size rather than the `solid` keyword), OBJ, PLY (ASCII and both binary byte orders), OFF, glTF 2.0 (`.gltf` with external or data-URI buffers, and packed `.glb`), and 3MF. Only geometry is read; materials come from the scene. Faces with more than three corners are fanned into triangles, glTF node transforms are baked into world space, and glTF needs a JSON reader that `utils/Json` provides, because the project has no JSON dependency. `Mesh.toHittables` turns each facet into a `Triangle` - Moller-Trumbore intersection, barycentric u/v, and a normal taken from the winding rather than from the file, since mesh files frequently carry wrong ones.

Model files agree on no units or origin, so `standingOnFloor()` is the default placement: the model is centred over the origin in x/z, rests on y=0 - the top of the ground sphere every scene uses - and is scaled to `DEFAULT_TARGET_HEIGHT`; pass `targetHeight = null` to keep the authored size. `BookScenes.modelWorld(path, material)` assembles that default scene (checkered ground + model) and always wraps it in a `BvhNode`. Run it with `mvn exec:java -Drt.scene=model -Drt.model=<path>`; scenes live in `scenes/BookScenes` and are picked by name (the old `1|2|3` still work), and the path also comes from `MODEL_FILE` or `./model.stl`. Triangles get their own leaf kind in the GPU buffers (`SceneBuffers.LEAF_TRIANGLE`) and their bounding boxes are padded through `Aabb.padded()`, since a facet in an axis-aligned plane would otherwise have a box no ray can enter.

## Scenes and Sampling
Every scene from the three books lives in `scenes/BookScenes` as a named builder returning a
`SceneDefinition`; `-Drt.scene=<name>` picks one (`cornell-final`, `final-week`, `cornell-smoke`,
`perlin-spheres`, `quads`, …, and the old `1|2|3` still resolve). `-Drt.samples`, `-Drt.width`,
`-Drt.depth` and `-Drt.aspect` scale and reframe any scene from the command line, since the books quote their finales at sample
counts that take hours, and `-Drt.out` redirects the render away from the committed `image.ppm`.

Shading follows The Rest of Your Life. A material returns a `ScatterRecord`: a diffuse surface
hands back a density to sample (`CosinePdf` around the normal, `SpherePdf` inside fog) while a
mirror or glass hands back the single ray it sends, and the renderer divides each sample by the
density it came from. A scene may also name `Camera.lights` - shapes worth aiming at - and then
half of every diffuse bounce's samples go straight at a light (`MixturePdf` over `HittablePdf`
and the surface's own density), which is what clears the noise out of a dim room; `-Drt.lights=off`
renders the same scene without it. `Quad` and `Sphere` implement `pdfValue`/`random` for this, and
the GPU carries the light list as bare geometry separate from the tree it traverses. Emissive
surfaces only emit through their front face.

## Build, Test, and Development Commands
- `mvn compile` — compiles Kotlin sources with the Kotlin Maven plugin targeting JVM 17.
- `mvn clean package` — recreates the shaded jar under `target/` and is the baseline for CI.
- `mvn exec:java` — runs `MainKt`, generating/overwriting `image.ppm`; commit only curated outputs.
- `mvn test` or `mvn -Dtest=CameraTest test` — executes unit tests (add them under `src/test/kotlin`).
- `GpuCpuComparisonTest` and `ImageRegressionTest` need a CUDA device and skip themselves without one. They compare against CPU renders stored before the CPU path tracer was removed; those references are frozen and cannot be rendered again, so a scene added to the comparison needs a reference made some other way. `UPDATE_REFERENCE_IMAGE` no longer exists.

## Coding Style & Naming Conventions
Follow idiomatic Kotlin style: 4-space indentation, `UpperCamelCase` for classes such as `HittableList`, `lowerCamelCase` for functions/properties, and `SCREAMING_SNAKE_CASE` only for constants. Keep packages under `rayTraceTypescript.*` to mirror directories. Favor `val` over `var`, keep mutable lists encapsulated (as in `HittableList`), and document non-obvious math near vector or material logic. Reuse helper extensions (e.g., `Vector.minus`) instead of ad-hoc calculations to preserve consistency.

## Testing Guidelines
Add tests beside the mirrored package in `src/test/kotlin`, using Kotlin Test or JUnit 5 so Maven Surefire can discover them. Name test classes `<Class>Test` and methods `fun rendersBlurredBackground()` so failures read naturally. Test deterministic pieces (vector math, material scatter logic, random helpers with seeded RNG) and gate image regressions by comparing computed pixel statistics rather than raw ppm bytes. Run `mvn test` locally before pushing; target coverage that hits every material branch at least once.

## Commit & Pull Request Guidelines
Git history shows short imperative messages (`add .gitignore`, `finished ray tracing in one weekend`), so keep titles under ~72 characters, starting with a verb (`tune camera depth`). Each PR should describe the scene/camera changes, list commands run (e.g., `mvn clean package`), attach before/after crops of `image.ppm` when visuals change, and link tracking issues. Avoid bundling refactors with feature additions; open follow-up tickets for larger rewrites.

## Rendering Output & Assets
Generated `image.ppm` files can be large; ignore intermediate renders and only commit canonical samples referenced in docs. When tweaking `camera` defaults (aspect ratio, samples, depth), capture the rationale in PR notes so reviewers understand performance vs. fidelity trade-offs. Store environment-specific configs (e.g., higher sample settings) in local profiles rather than changing `Main.kt` defaults.

Every render writes a PNG beside its PPM (`render/PpmWriter`, same pixels); `-Drt.pfm` adds the unclipped linear pixels as a PFM. Renders started from `Main` are denoised by default (`-Drt.denoise=off` disables it): beside the raw image they write `<name>-denoised.ppm/.png`: after the image, the kernel renders two guides (`AOV_MODE`: first-hit albedo and normal, 256 spp) and `render/Denoiser` runs Intel Open Image Denoise's RT filter on the CPU, calling its DLL through LWJGL's libffi. The Windows DLLs ship in `native/oidn/windows-x64` (see its README), so a clone denoises as is; `-Drt.oidn` or `OIDN_DIR` point elsewhere. Missing DLLs only skip the denoising, with a message. `-Drt.aov=albedo|normal` renders a guide on its own.

## Turntable Films
A turntable film turns the scene's objects in place while the camera, the lights and the room stand still - what StlViewer's "Film obrotowy" looks like (it turns its camera with the lamps and wall instead). `-Drt.turntable=film.mp4` renders one from the command line (`gpu/TurntableRender`: the parts that are neither lights nor walls, or `-Drt.turntable.parts=a;b`, about the middle of their footprint; `-Drt.turntable.seconds|turns|fps|reverse|quality=max`, `-Drt.samples`); the viewer's panel button *Film obrotowy…* opens `gui/TurntableDialog` (the selected object, else all added ones, else the scene's own), and `-Drt.gui.film=film.mp4` starts that path without clicks. `gpu/TurntableFilm` traces each frame in ~100 ms slices with its own seed and 32-sample guides, and denoises and writes it on a worker while the GPU traces the next; `render/VideoEncoder` pipes the frames to ffmpeg (`-Drt.ffmpeg`, `FFMPEG` or the PATH; H.264 High, yuv420p, BT.709, key frame every 2 s, StlViewer's bitrates), renders one turn and copies it for the others, and writes `<name>.part.mp4` until the film is whole, so a cancelled or failed film leaves nothing. `gpu/Placement` folds a move of a `PlacedMesh` into its placement, so turning one costs a tree copy per frame, not a rebuild; `studio-model` (StlViewer's gold-reel studio, for comparing the two renderers) builds its figure that way.

## Interactive Viewer
`-Drt.gui` opens the chosen scene in a window (`gui/Viewer`) instead of rendering to a file: left drag orbits around the point the camera looks at, Shift + left drag or middle drag pans, the wheel or right drag dollies, Ctrl + click stands the selected model on the floor under the cursor, R resets, D toggles denoising, S asks for a file name (suggested `viewer-<scene>-<time>` beside `-Drt.out`) and saves PPM/PNG plus the denoised copy, Ctrl+S / Ctrl+O save and load the whole scene as a `.rtscene` text file (`gui/SceneFile`: base scene and its switches, camera, image settings, mode, lights and parts, each added object with its model path relative to the file; `-Drt.gui.load=file` opens one from the command line, picking its base scene), +/- change the field of view, Delete removes the selected model. The scene's own objects (`BuiltInObject`) move and turn like added ones - both are `Movable` - by standing them in `Translate(RotateY(...))` about their footprint and moving their light-sampling stand-in along; "Przywróć obiekty sceny" puts them back. Parts marked `isSurface` (the Cornell box walls) are `WallObject`s instead: fixed in place, their material editable (a changed wall is rebuilt as the same quad); added objects and walls share `HasMaterial`, and scene files keep changed walls as `wall.N.*`. The side panel (`gui/ControlPanel`) sets the resolution and the sample target and adds models from any format `MeshLoader` reads (`gui/PlacedObject`: position, turn, height, finish, z-up for 3D-printing files); `-Drt.gui.models=a.stl;b.obj` opens with models placed. A mesh may carry per-face materials (`Mesh.faceMaterials` into `Mesh.palette` of `MeshMaterial`, read from an OBJ's `mtllib`/`usemtl` and .mtl `Kd`, `Pm`, `Pr`, `Ke`, `d`, `Ni`); transforms keep them, `MeshBlock` carries them in leaf order, `PlacedMesh.palette` and `toColouredHittables` use them, and `cornell-model` keeps them unless `-Drt.model.material` is given (it also stands only STL/3MF up from z). It opens in the quick look for setting a scene up (kernel `AOV_MODE 3`: first hit shaded by its colour under a head light, glass seen through, 16 jittered rays per pixel at full size); T or the panel's *Tryb* switches to ray tracing, and `-Drt.gui.raytrace` opens in it. Object edits rebuild the GPU scene 80 ms after the last change, in the same `GpuSession` (`replaceScene` swaps the scene buffers and keeps the kernels while the feature switches match). A loaded model keeps a `gpu/MeshBlock` - its triangles and SAH tree built once in its own space - and is placed as a `PlacedMesh` (scale, turn about y, offset): the flattener copies that tree in transformed and grafts it into the scene's tree as one primitive, so moving, turning or resizing a 400k-triangle model costs ~130 ms instead of a ~2 s rebuild. In ray tracing, while the camera moves it renders a quarter-size image at 1 spp; once it holds still for 150 ms it accumulates full-size samples, denoising at 16, 64, 256… spp. The look is FlatLaf's dark theme (`com.formdev:flatlaf`, set up in `gui/Theme` before any component is made) with an amber accent; shortcuts go through a window-wide key dispatcher, so they work whatever holds the focus except text fields. It shares `gpu/GpuSession` with the file renderer: scene buffers uploaded once, one kernel per mode, the camera and resolution passed per launch, and a second output buffer for the denoiser guides.
